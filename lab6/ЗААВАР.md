## 2. Онол

**Уралдааны нөхцөл (race condition)** — хэд хэдэн процесс/урсгал дундын өгөгдөлд зэрэг хандаж, үр дүн нь гүйцэтгэлийн **дарааллаас** хамаарах. Жнь `counter++` нь машины түвшинд `reg = counter; reg = reg + 1; counter = reg` — дунд нь контекст сэлгэлт гарвал нэмэгдэл алдагдана (§6.1).

**Эгзэгтэй муж (critical section)** — дундын өгөгдөлд хандаж буй кодын хэсэг. Шийдэл 3 нөхцөл хангана:
1. **Mutual exclusion** — нэг удаад зөвхөн нэг процесс эгзэгтэй мужид.
2. **Progress** — хэн ч эгзэгтэй мужид байхгүй бол орох хүсэлтэй процессуудаас хойшлуулалгүй сонгоно.
3. **Bounded waiting** — орох хүсэлт гаргасан процесс хязгаартай хугацаанд орно.

**Хэрэгслүүд:**

| Хэрэгсэл | Санаа | Хүлээх арга |
|---|---|---|
| Тасалдал хаах | Нэг CPU-д сэлгэлт гарахгүй болгох | — (олон CPU-д ажиллахгүй, цагт нөлөөлнө — 6.1) |
| Атомар заавар | `test_and_set`, `compare_and_swap` — HW-ийн хуваагдашгүй заавар | — |
| **Мутекс** (spinlock) | `acquire()` / `release()` | Завгүй хүлээлт (spin) эсвэл унтах |
| **Семафор** | Бүхэл тоо `S`, `wait()` (P) / `signal()` (V); binary (0/1) эсвэл counting | Хүлээлтийн жагсаалтад унтах |
| **Монитор** | Мутекс + condition variable (`wait()` / `signal()`) — нэг удаад нэг урсгал дотор нь | Condition дээр унтах |

**Liveness асуудал:** түгжрэл (deadlock — бие биеэ хүлээх), starvation, priority inversion.

## 4. Programming Problems 6.33–6.34

### 6.33 a, b — Уралдаан хаана байна вэ? (`race.c`)

- **a. Өгөгдөл:** `available_resources` (бүх урсгалын дундын глобал хувьсагч).
- **b. Байрлал:**
  1. `decrease_count()` — `if (available_resources < count)` **шалгалт** ба `available_resources -= count` **хасалтын хооронд**: хоёр урсгал зэрэг шалгалтыг давж, нөөцийг **хэтрүүлж** авна (check-then-act).
  2. `available_resources -= count` болон `increase_count()`-ийн `available_resources += count` — **унших-өөрчлөх-бичих** атомар биш → нэмэлт/хасалт **алдагдана** (lost update).

> Олон цөмт системд уралдаан ховор гардаг тул `CONTEXT_SWITCH_WINDOW()` (20 µs саатал) нэмж "яг энэ мөчид сэлгэлт гарвал" нөхцөлийг дуурайсан. Шударга харьцуулалтын тулд `mutex.c`, `monitor.c`-д ч эгзэгтэй муж **дотор** ижил саатал бий.

### 6.33c — Мутексээр засах (`mutex.c`)

```c
pthread_mutex_lock(&lock);              // ---- эгзэгтэй муж ----
if (available_resources < count) { pthread_mutex_unlock(&lock); return -1; }
available_resources -= count;           // шалгалт + хасалт хамтдаа хамгаалагдсан
pthread_mutex_unlock(&lock);
```
`increase_count()`, `get_available()` ч мөн адил lock дотор. Нөөц хүрэлцэхгүй бол номын интерфейсийн адил **-1** буцаана (дуудагч дахин оролдоно).

### 6.34 — Монитор + condition variable (`monitor.c`)

```c
pthread_mutex_lock(&monitor_lock);
while (available_resources < count)                       // while — сэрсний дараа дахин шалгана
    pthread_cond_wait(&enough_resources, &monitor_lock);  // lock-оо чөлөөлж УНТАНА
available_resources -= count;
pthread_mutex_unlock(&monitor_lock);
...
// increase_count():
available_resources += count;
pthread_cond_broadcast(&enough_resources);                // хүлээж буй бүх урсгалыг сэрээнэ
```
- Дуудагч `while (decrease_count(count) == -1);` гэж **завгүй хүлээх шаардлагагүй** — `decrease_count(count);` л дуудна.
- **`while`, `if` биш:** сэрсэн мөчид өөр урсгал түрүүлж авсан байж болно, мөн spurious wakeup.
- **`broadcast`, `signal` биш:** хүлээгчид өөр өөр тоо (1–3) хүсдэг тул нэгийг сэрээхэд тэр нь хангалтгүй байж болно.
- `count > MAX_RESOURCES` бол **шууд -1** — эс бөгөөс үүрд хүлээнэ.

### Тест (`test_harness.c`)

8 урсгал × 300 давталт: 1–3 нөөц авах → 0–50 µs "ашиглах" → буцааж өгөх. Шалгах нөхцөл:
1. **Peak held ≤ 5** — нэгэн зэрэг эзэмшиж буй нөөц MAX-аас хэтрэхгүй.
2. **Final available == 5** — бүгд буцаагдсан.

(Тестийн өөрийн тоолуурууд `stdatomic` атомар тул тэдгээрт уралдаан байхгүй.)

## 7. Багш асууж магадгүй асуултууд

| Асуулт | Товч хариулт |
|---|---|
| Мутекс ба семафорын ялгаа? | Мутекс — 0/1, эзэмшигч нь л чөлөөлнө (ownership). Семафор — тоо (counting), өөр урсгал `signal` хийж болно; N нөөцийг тоолоход тохиромжтой. |
| 6.33-ыг семафороор яаж засах вэ? | `sem_t mutex; sem_init(&mutex, 0, 1);` → `sem_wait(&mutex); ... sem_post(&mutex);` — binary семафор мутекстэй адил. Counting семафор (утга 5) нь зөвхөн 1 ширхэгээр авахад тохирно; олон ширхэгийг нэг дор авахад хагас авч түгжрэл үүсэх эрсдэлтэй. |
| `pthread_cond_wait` яагаад мутекс авдаг вэ? | Унтахаасаа өмнө мутексийг **атомараар** чөлөөлж, сэрэхдээ дахин авна — шалгалт ба унтах хоёрын хооронд signal алдагдахаас (lost wakeup) сэргийлнэ. |
| Spurious wakeup гэж юу вэ? | Signal-гүйгээр сэрэх (POSIX зөвшөөрдөг) — тиймээс нөхцөлийг `while`-аар шалгана. |
| Монитор дахь signal-and-wait vs signal-and-continue? | Hoare: signal хийсэн нь хүлээж, сэрсэн нь шууд ажиллана. Mesa (pthreads, Java): signal хийсэн нь үргэлжилнэ, сэрсэн нь дараа нь ажиллаж нөхцөлөө дахин шалгана. |
| Priority inversion? | Бага эрэмбэтэй процесс түгжээ эзэмшиж байхад өндөр эрэмбэтэй нь хүлээж, дунд эрэмбэтэй нь бага эрэмбэтэйг буцаан авах. Шийдэл — priority inheritance. |
| Яагаад `CONTEXT_SWITCH_WINDOW` нэмсэн бэ? | Уралдааныг тогтвортой харагдуулахын тулд. Саатлыг бүр арилгаад (`((void)0)`) `./race 12 20000` ажиллуулахад ч 3/3 удаа илэрсэн: peak held **31–35**, final available **19–52** — алдаа "ховор" гэдэг нь "байхгүй" гэсэн үг биш. |
| Түгжрэлийн 4 нөхцөл? | Mutual exclusion, hold and wait, no preemption, circular wait (Lec7). |
